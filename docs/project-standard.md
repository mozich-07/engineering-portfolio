# 项目管理规范

## 归档与拆库

- 以 `catalog.json` 为目录索引，使用固定主键 `Pxx`，目录名使用小写英文和连字符。改展示名不改 ID，不把同源原型重复当作交付。
- 每个条目的 README 写清目的、功能、本人工作、复现状态和待办。学习实验保留在总库；能独立构建、有持续迭代或独立发版需求时，再拆成单独仓库，并从总库回链。
- 不为每个项目建空目录。有文件再按需添加：`firmware/`（嵌入式工程）、`src/`（应用源码）、`hardware/`（原理图、PCB、BOM）、`tests/`（测试）、`docs/`（架构与验收）和 `assets/`（获准发布的截图）。保留现有工具链要求的入口，如 Arduino 草图与目录同名。

## 从开发到交付

1. Issue 写清问题、预期、验收条件和项目 ID。用 `feat/p39-import` 或 `fix/p36-mode-switch` 一类短分支；每次改动优先解决一件事。
2. PR 说明变更、影响、验证命令和实测结果。硬件列板卡、接线、供电、编译环境和台架测试；软件列输入、环境、预期、实际与失败边界。图不是测试通过的替代品。
3. `main` 只保留可阅读或已验证的版本；“仅文档”“有源码”“已复现”分开标注。首次交付遵循最小可运行原则，不堆叠依赖、完整课程包或模型文件。
4. 有稳定交付后才记版本。单个项目仍在总库时用如 `p39/v0.1.0` 的标签，并记录变更和硬件/依赖版本；没有验收记录暂不打正式标签。

## 发布验收

- [ ] 角色表述与真实交付一致；大创仅写本人职责、团队成果及必要来源，不列其他成员。
- [ ] 检查团队授权、课程要求、第三方代码/模型/配图许可；上游许可和署名不剥离。未选定许可时，不默认整仓开放授权。
- [ ] 用自制或获准分发的样例；不纳入联系方式、证件、报告原件、原始题库、私有路径、口令或缓存。私有仓库也遵守此规则。
- [ ] 复核待提交文件，运行 `python tools/check_repo.py` 并再跑项目自身测试；仅在实际运行后更新复现状态。
